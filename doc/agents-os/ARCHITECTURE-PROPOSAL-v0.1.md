# Architecture Proposal v0.2 — Paperclip × Agents-OS Core × Hermes

**Status:** Revised after Cursor adversarial review (AAD-52). Still draft; not approved architecture.

## What changed after Cursor

Cursor found a material conflict with accepted ADR-0060: v0.1 treated the Paperclip backend as an active organizational control plane, while ADR-0060 explicitly permits Paperclip as presentation and excludes the Paperclip backend as a second runtime authority. That conflict is now explicit and unresolved pending Direction or a formal ADR change.

Cursor also identified high double-governance risk across Paperclip approvals, task/run lifecycle, wakeups and Core/QMS Gates. This is accepted as a valid architectural warning.

One Cursor claim is disputed by repository evidence: this fork contains both `packages/adapters/hermes` and `packages/adapters/hermes-gateway`, plus Hermes gateway join/smoke/E2E scripts. The open question is whether those adapters satisfy the governed principal-agent contract, not whether Hermes integration exists.

## Claim disposition

- Paperclip as organization/operator UX: `SUPPORTED`.
- Paperclip backend as co-equal authority with Core: `REJECT` under current ADR-0060.
- Core immutable/versioned in operation mode: `SUPPORTED`.
- Core service/sidecar + thin integration shim: leading working hypothesis, `SUPPORTED` but not yet proven.
- Hermes as replaceable cognitive/runtime provider: `SUPPORTED` experimentally.
- Hermes as canonical CEO identity/memory authority: `REJECT`.
- One principal identity across Paperclip/OpenWebUI: requirement `SUPPORTED`; implementation remains `UNKNOWN`.
- Linear as engineering SSoT for missing-capability work: `SUPPORTED`; it is not user-memory/business-domain SSoT.
- Missing-capability escalation lifecycle: `WEAK`; requires concrete correlation and round-trip status tests.

## Revised responsibility split

### Paperclip frontend
Presentation/operator surface for hierarchy, work state, approvals and activity. It may project Core/QMS state but must not independently own lifecycle, gates, cost, locks or durable wakeups while ADR-0060 remains accepted.

### Paperclip backend
Experimental/reference implementation under the current normative baseline. Its adapters, heartbeat code, approval models, MCP gateway and Hermes integration are valuable implementation evidence and may be exercised in isolated falsification tests. Promotion into the target runtime requires an explicit superseding decision.

### Agents-OS Core
Canonical governance/runtime boundary for identity, capability/authority evaluation, policy, Human Gates, evidence requirements and governed execution authorization. Core exposes versioned interfaces and is not source-editable by the operational agent.

### Hermes
Replaceable cognitive/runtime provider for the principal-agent experiment. Hermes-local state cannot by itself define durable identity, authority or canonical memory.

### OpenWebUI
Conversational channel bound to the same canonical principal identity and governed durable memory namespace.

### Linear
Operational SSoT for engineering escalations and implementation status generated by missing capabilities.

## H1 — Canonical governance first

Target path:

`Paperclip/OpenWebUI presentation → Core application/operational boundary → governed work/execution → provider adapter (Hermes or other) → tool`

The Paperclip backend path remains a lab comparator, not the canonical architecture while ADR-0060 stands.

## H2 — Core distribution: service + thin shim

Leading hypothesis: Core runs as a versioned service/sidecar boundary with a thin adapter/shim at execution entry points. The shim transports identity, requested capability, work context and evidence requirements; it does not implement policy independently.

**Falsification:** if safe synchronous authorization cannot be inserted without duplicating lifecycle/locks or unacceptable coupling, this hypothesis fails.

## H3 — One principal actor, governed memory

The principal/CEO is a canonical agent identity independent of Hermes, Paperclip or OpenWebUI. Hermes sessions and Paperclip task sessions are runtime/channel state, not identity authority.

Memory classes:

1. governed durable facts/decisions;
2. conversation history/bindings;
3. task/run context;
4. provider-local transient learning/session state.

Only governed scopes may provide cross-channel continuity by default.

## H4 — Correlated engineering escalation

When capability is unavailable or unauthorized:

`user_need → capability evaluation → CAPABILITY_UNAVAILABLE/ESCALATION_REQUIRED → EscalationRecord → Linear issue → engineering decision/status → user-visible status update`

Minimum correlation fields:

- principal/actor id;
- conversation id;
- originating work/request id;
- capability key;
- evidence/reference ids;
- Linear issue id;
- escalation status;
- implementation/project reference if approved.

Linear owns engineering work state; the conversation/business system owns request provenance and the user relationship.

## Approval invariant

There must be one semantic authorization decision. Under the current baseline, Core/QMS Human Gate is authoritative. Paperclip may project and submit that decision, but a separate Paperclip approval record must be non-authoritative/reconstructible or absent from the target runtime.

## Minimal falsification experiment

### Slice A — Shopify capability escalation without Paperclip backend

A non-technical Shopify operator asks in OpenWebUI to change a controlled content item. Core evaluates capability. If write capability is unavailable, the system creates a correlated Linear escalation and returns a user-visible tracking reference. After engineering status changes, the principal can report the current state.

Falsifies H3/H4 if deterministic capability detection, correlation or round-trip status fails.

### Slice B — Paperclip/Hermes adapter governance comparator

Use the existing Hermes/Hermes Gateway adapter path with one heartbeat-triggered task. Insert a Core pre-execution authorization call before material execution and verify that denied capability cannot bypass through another adapter/tool path.

Falsifies H1/H2 if the check can be bypassed, creates duplicate lifecycle authority, or cannot preserve task/run identity.

## Explicit disagreements retained for Codex

1. Current project intent wants Paperclip as the organizational base, but ADR-0060 excludes its backend from the target runtime. This is a normative conflict, not resolved by this revision.
2. Cursor recommends the canonical CEO specifically as QMS `AgentProfile`; the newer `agents-os-core` identity model still requires direct verification.
3. Cursor treats Hermes CEO as contrary to earlier doctrine. This project instead treats Hermes as an experimental replaceable runtime, never authority; whether that is an acceptable exception remains open.
4. Durable memory location remains undecided. Governed documents/conversation bindings are stronger than Hermes-local state, but the concrete storage contract is unknown.
5. Cursor's statement that Hermes lacks a native adapter is contradicted by this fork's `hermes` and `hermes-gateway` adapter packages and smoke/E2E tooling.

## Next review
